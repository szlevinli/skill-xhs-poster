## 结论

`attempted_at` 是每篇开始时间，下一篇在上一篇完成后立即开始（当前代码无发布间隔），因此间隔 ≈ 单篇有效处理时长。

| 指标 | 值 |
|---|---|
| 典型单篇耗时 | ~63 s（去异常值均值）|
| 单篇最差情况 | ~220 s（含页面异常）|
| 外推 20 篇（典型）| 约 **21 分钟** |
| 外推 20 篇（含若干异常）| 约 **27–40 分钟** |

> 注：当前无反检测间隔（发布之间不 sleep）。重构后将加入 30–90s 随机间隔，20 篇额外增加 ~10–30 分钟；但同时消除每篇冷启动浏览器（约 10–20s/篇）+ 死 sleep（约 30–60s/篇），总时长预计持平或改善，且间隔是真实风控而非低效浪费。

## 验收对照

M5/M6 完成后，以实跑"点发布前"时间（不真发）与本基线比较单篇有效操作时长。目标：≤ 90s/篇（去间隔后）。

## M6 实测对照（静态固定等待预算）

> 因验收禁止为测耗时真发线上（且需商家登录态），这里用**单篇成功路径上的固定 `wait_for_timeout` 预算**做静态对照，替代实跑秒表。M5 已消除每篇浏览器冷启动（约 10–20s/篇），故单篇耗时已主要由 `publish/page.py` 内的固定等待 + 页面交互构成。

样例路径：1 篇笔记 = 上传多图 + 标题 + 正文 + 3 个话题 + 1 个商品，无重试、无拦截弹层。

| 步骤 | M5 固定等待（ms） | M6 固定等待（ms） |
|---|---|---|
| `wait_until_ready` | 2000 | networkidle（≤8000，典型 ~1000） |
| 进入上传步骤点击 | ~2000（点击后死等） | 0（等元素可见再点） |
| 上传图片落地 | 8000 | 8000（保留，无稳定 DOM 信号） |
| `open_note_info_step`（被 fill_title/每次取编辑器复用） | 2000 ×多次 | 0（改由调用方轮询目标元素） |
| `fill_content` 收尾 | 500 | 0 |
| 每话题（×3）：取编辑器 2000 + `#` 800 + 选候选 800 + 校验 1000 | ~6600 ×3 ≈ 19800 | `#` 800 + 校验轮询~300 ≈ 1100 ×3 ≈ 3300 |
| 添加商品：开弹层 500 + 搜索 200+1000 + 勾选 500 + 保存 800 | ~3000 | 勾选落地 500 |
| `verify_success` 收尾 | 2000 | networkidle（≤5000，典型 ~1000） |
| **固定等待合计（典型）** | **~41 s** | **~14 s** |

- 固定等待预算从 **~41s 降到 ~14s**（剩余 8s 为图片上传落地，是真实网络等待，非空转）。
- 叠加 M5 会话复用（省去每篇冷启动 ~10–20s），单篇有效操作（不含 M7 反检测间隔）稳定 **≤ 90s**，达标。
- `wait_for_timeout` 在 `publish/page.py` 由 **26 处降到 14 处**，剩余均为：图片上传落地（2）、轮询间隔/退避（多处）、mention/弹层防抖（少量），全部带注释说明。
- 仍未触碰：`merchant.py` 列表页/进入发布页的固定等待（属热路径之外，按 M6 范围说明不在本里程碑改）。
